Projet 8 : où en est-on ?

Un point complet, en langage simple, sur la mission, ce qui fonctionne déjà, ce qui reste à faire et ce que vous devrez faire vous-même.

Résumé très court : le dépôt GitHub public, l’API, les tests, Docker et le pipeline GitHub Actions sont en place. L’API est déployée sur Render. Après les contrôles CI réussis, Render déploie automatiquement la branche main. Les logs structurés, l’export local, le stockage SQLite et une première mesure de dérive sont disponibles. Il reste l’étude d’optimisation et une référence de production gouvernée.

1. Le contexte de la mission

Le document OpenClassrooms raconte une mise en situation professionnelle : vous êtes Data Scientist. Une responsable, Chloé Dubois, vous demande de mettre un modèle de scoring en production pour qu’il puisse répondre presque en temps réel.

Dans l’histoire du sujet, l’entreprise s’appelle « Prêt à Dépenser » et le service s’appelle « Crédit Express ». Dans votre vrai travail précédent, le modèle porte le nom Matchers : il estime le risque qu’un dossier déjà gagné ne soit pas mené jusqu’à sa finalisation. C’est ce modèle réel qui est repris ici.

Le but métier

Recevoir les informations d’un dossier, calculer un score de risque, puis aider une équipe à décider si le dossier mérite une attention particulière.

Le but technique

Montrer que vous savez passer d’un modèle de data science à un système utilisable, testé, déployable et surveillé.

Le but de la soutenance

Expliquer vos choix, montrer l’API et la CI/CD, puis discuter de fiabilité, dérive des données, performance et maintenance.

3. Ce qui a déjà été fait

Le dépôt et l’historique Git

Un dépôt public a été créé sur GitHub : github.com/hgbe-GH/Projet8-scoring-api. Il est sur la branche main, et GitHub reçoit bien les commits.

L’historique est volontairement découpé en petites étapes : conception, contrat du modèle, validation des entrées, chargement du modèle, logs, API, Docker, CI/CD et documentation de compatibilité. C’est exactement ce qui permet de montrer une progression claire pendant la soutenance.

Le modèle repris depuis Projet6

  • Le fichier du modèle est models/matchers_option_a_model.joblib.
  • Ses métadonnées sont dans models/matchers_option_a_metadata.json.
  • Il utilise 44 variables d’entrée.
  • Il renvoie une probabilité de risque entre 0 et 1.
  • Le seuil métier enregistré est 0.06. Si le score est supérieur ou égal à ce seuil, l’API renvoie risk_flag: true.
  • Les données brutes du Projet6 ne sont pas copiées dans ce dépôt. C’est important pour éviter de publier des données sensibles.

L’API créée

L’API repose sur FastAPI. Elle a deux routes :

  • GET /health : répond que le service est prêt et indique la version du modèle.
  • POST /predict : reçoit les 44 informations d’un dossier et retourne le score, le seuil, le drapeau de risque, le nom et la version du modèle.

La documentation interactive est automatiquement disponible sur /docs quand l’API tourne. Elle permet d’essayer l’API sans installer Postman.

Point technique important, traduit simplement : le modèle ne se recharge pas à chaque appel. Il est chargé une fois au démarrage de l’API, puis réutilisé. Cela évite de ralentir l’API et répond à un point de vigilance précis du sujet.

La validation et les erreurs

Les 44 champs sont actuellement obligatoires. Si un champ manque, si du texte est envoyé à la place d’un nombre, ou si des heures prévues sont négatives, l’API répond avec une erreur claire 422. Une erreur de chargement du modèle donne 503. Une erreur interne de prédiction donne 500 sans divulguer le détail technique au client.

Les logs et le monitoring

Chaque appel /predict produit un événement JSON avec timestamp, latence, statut, version du modèle et, en cas de succès, score, décision et entrées validées. Les erreurs ne contiennent ni entrées brutes ni détails techniques. L’événement est écrit localement et dans les logs Render avec le préfixe ML_EVENT.

Le flux gratuit est : Render → export des logs → import idempotent dans data/monitoring/monitoring.db → rapport local. Le script analyse le taux d’erreur, la latence p95, le PSI numérique et les catégories nouvelles. Bases, exports et rapports sont ignorés par Git.

Les tests

La suite automatisée couvre le modèle, les 44 champs, les erreurs de saisie, la prédiction, le chargement unique, les logs, les routes HTTP, la CI/CD, le stockage SQLite et l’analyse de dérive.

La dernière vérification Docker a donné : 26 tests réussis, 0 échec.

Docker

Le fichier Dockerfile permet de construire une image complète. Elle utilise Python 3.12, car c’est la version enregistrée avec le modèle dans MLflow. Le modèle est ainsi relancé dans un environnement compatible.

Le test Docker a réellement construit l’image, démarré un conteneur, puis appelé /health avec succès. Le conteneur de test est nettoyé ensuite.

La CI/CD GitHub Actions

Le fichier .github/workflows/ci.yml se déclenche à chaque pull request et à chaque push sur main. Il effectue les étapes dans l’ordre :

  1. installer les dépendances et lancer les tests ;
  2. construire l’image Docker ;
  3. démarrer l’image et tester /health ;
  4. autoriser le déploiement automatique sur Render après le succès des contrôles.

La première exécution GitHub est terminée avec succès : ouvrir le run CI/CD réussi.

4. Ce qui reste à faire

Priorité 1 — conserver la preuve du déploiement

L’API est disponible sur projet8-scoring-api.onrender.com/health. Render reconstruit l’image Docker et vérifie /health après un push dont la CI GitHub est réussie. Une capture des pages GitHub Actions et Render permettra de le démontrer à la soutenance.

Priorité 2 — renforcer l’analyse de dérive

Le PoC de monitoring est en place. Il lit les événements stockés localement et répond déjà à ces questions :

  • les scores deviennent-ils soudainement très différents ?
  • les valeurs envoyées à l’API ressemblent-elles encore aux valeurs utilisées pour entraîner le modèle ?
  • la latence augmente-t-elle ?
  • y a-t-il trop d’erreurs 422, 500 ou 503 ?

La démonstration utilise une référence synthétique et prouve le mécanisme, pas une dérive réelle. Pour une conclusion de production, il faudra une référence stable provenant du Projet6, gouvernée et non publiée.

Priorité 3 — faire évoluer le stockage si le service grandit

Le PoC conserve durablement les exports dans SQLite localement. En production réelle, il faudra remplacer ou compléter cette solution par un stockage centralisé, chiffré et soumis à des règles de rétention.

Priorité 4 — étudier la performance

Une fois l’API déployée et utilisée, il faudra mesurer le temps de réponse et le temps d’inférence. Ensuite, on choisira une optimisation utile, par exemple simplifier le code, modifier l’environnement, ou tester un format de modèle plus rapide. L’important est de montrer une comparaison avant/après sans dégrader la qualité du modèle.

Priorité 5 — préparer la soutenance

Vous devrez pouvoir montrer le dépôt, les commits, le fichier Docker, le workflow, un appel API réussi, les résultats du monitoring et l’amélioration de performance. Il faudra aussi expliquer les choix : pourquoi FastAPI, pourquoi Docker, pourquoi ce stockage de logs et comment vous détectez la dérive.

5. Vos prochaines actions concrètes

  1. Conserver les liens et captures du workflow GitHub Actions et du déploiement Render.
  2. Conserver les exports Render et les rapports de monitoring lors de la démonstration.
  3. Fournir une référence Projet6 gouvernée pour remplacer la référence synthétique.
  4. Mesurer puis optimiser les performances de l’API.
