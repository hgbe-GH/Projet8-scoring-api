01 · Contexte

Pourquoi ce projet existe.

Le Projet 8 reprend un modèle de scoring produit dans le Projet 6 et le place dans un cadre proche de la production. L’enjeu ne consiste pas seulement à obtenir un score : il faut servir le modèle, tracer les prédictions, surveiller les données et rendre le résultat compréhensible.

Besoin métier

  • Recevoir un dossier et calculer son risque presque en temps réel.
  • Appliquer un seuil métier de 0,06 pour produire un drapeau de vigilance.
  • Conserver une trace exploitable de chaque prédiction.
  • Repérer les changements entre les données de référence et les données reçues.

Objectif technique

  • Exposer le modèle avec une API FastAPI documentée par Swagger.
  • Construire une image Docker reproductible et la publier sur Render.
  • Persister localement les événements dans SQLite.
  • Analyser le drift avec Evidently et l’afficher dans Streamlit.

02 · Architecture

Le flux complet, de la requête au dashboard.

01 / SERVIRRender + FastAPI

Expose /predict, /health et Swagger.

02 / TRACERLogs ML_EVENT

Écrit l’identifiant, les entrées, le score, le statut et la latence.

03 / STOCKERSQLite local

Importe les événements de façon idempotente grâce à event_id.

04 / COMPAREREvidently AI

Compare six variables entre référence et période courante.

05 / LIREStreamlit

Présente volumes, erreurs, latence, drift et preuve de stockage.

Choix d’architecture : l’API publique tourne sur Render. SQLite, les données de référence privées, Evidently et Streamlit restent en local. Ce choix évite de dépendre du disque éphémère du service Render gratuit et garde les données de monitoring hors du dépôt Git.

04 · Modèle et données

Pourquoi le modèle n’a pas été réentraîné.

L’artefact du Projet 8 et celui du Projet 6 sont identiques octet par octet. Les contrôles ont montré que le problème venait du contrat d’entrée de l’API, pas du modèle.

ContrôleRésultat vérifiéDécision
Population994 dossiers d’entraînement et 248 de validation temporelle.Effectifs conformes aux métadonnées.
Reproduction des scores248 dossiers acceptés sur 248 ; différence maximale 0,0.Conserver le modèle actuel.
ClassementROC AUC 0,7764 ; average precision 0,7741.Le modèle sépare utilement les groupes sur le holdout.
Seuil 0,0693 vrais positifs, 153 faux positifs, 0 faux négatif, 2 vrais négatifs.Garder le seuil documenté, avec une vigilance sur le volume d’alertes.
RéentraînementAucun nouveau jeu étiqueté indépendant.Ne pas remplacer le modèle sans preuve de gain.
Point à dire : le seuil de 0,06 protège fortement contre les faux négatifs, mais signale 246 dossiers sur 248. Il correspond à une vigilance très large et devra être réévalué avec des données de production étiquetées et une validation indépendante.

05 · Evidently AI et Streamlit

Ce que le dashboard surveille.

Six variables suivies

  • heures_prevues
  • montant_demande_eur
  • pct_financement_demande
  • modalite
  • source_lead
  • type_financement

Indicateurs affichés

  • Nombre d’appels et taux d’erreur.
  • Latence moyenne et percentile 95.
  • Nombre et part de variables en drift.
  • Tests statistiques et distributions.
  • Nombre de lignes persistées dans SQLite.
  • Période couverte et dernier événement.

La référence privée utilise les 248 lignes complètes du holdout temporel du Projet 6. Les 994 lignes d’entraînement ne conviennent pas directement : source_lead manque sur 879 d’entre elles, ce qui créerait une référence biaisée après suppression des lignes incomplètes.

07 · Résultats

Comment commenter le drift sans surinterpréter.

Résultat de démonstrationLecture correcte
2 variables sur 6 détectées en drift.Le pipeline Evidently réagit aux changements introduits volontairement.
heures_prevues : PSI 11,77 et test K-S très significatif.La distribution simulée passe d’environ 15–35 heures à 60–90 heures : le décalage est massif.
modalite : 50 % de catégories nouvelles ; Jensen–Shannon ≈ 0,589.La catégorie hybride apparaît seulement dans la production simulée.
PSI supérieur à 0,20 sur deux autres variables sans alerte Evidently correspondante.Avec seulement 30 observations et dix tranches, le PSI est instable ; il faut plus de données.
30 appels, 0 erreur, p95 de 25 ms.Ce sont des valeurs générées pour prouver l’affichage, pas une mesure de performance Render.
Formulation recommandée : « Ce scénario synthétique valide la chaîne de détection. Il ne prouve pas qu’un drift existe déjà en production. Pour cela, je dois importer une période Render représentative et comparer les mêmes variables à la référence Projet 6. »

09 · Trame orale

Une explication simple en sept étapes.

Présenter le besoin

« Je pars d’un modèle de scoring déjà entraîné. Mon objectif est de le rendre accessible par API et de surveiller les données qu’il reçoit. »

Montrer l’architecture

« Render sert le modèle. Les prédictions produisent des logs structurés. Je les importe dans SQLite, puis Evidently compare la production à la référence et Streamlit affiche les résultats. »

Exécuter une prédiction

Ouvrir Swagger, coller le JSON fictif, lancer POST /predict, puis expliquer risk_score, threshold et risk_flag.

Prouver la qualité du contrat

« J’ai corrigé les booléens, les valeurs nulles et les zéros valides. Les 248 dossiers de validation reproduisent exactement les scores du Projet 6. »

Montrer SQLite

« La base contient 30 événements. Une deuxième importation n’ajoute aucun doublon grâce à la clé event_id. »

Commenter Evidently

« Deux variables sont détectées dans le scénario synthétique : les heures prévues et la modalité. Ces données prouvent la détection, pas un drift réel de production. »

Conclure avec les limites

« La chaîne technique est opérationnelle. La prochaine étape est d’importer une période représentative, puis d’obtenir les labels futurs avant de décider d’un réentraînement ou d’un nouveau seuil. »
